# 生成代码可手工维护架构与实施方案

状态：架构方案。本文定义生成器与运行时的目标行为；实际实施和验收进度以[实施记录](SVTYPES_GENERATED_CODE_EDITABILITY_IMPLEMENTATION.md)为准。

SV 生成默认使用显式类型，以扩大工具兼容性。本文关于辅助代码跟随手工类型修改的描述适用于
`use_type_reference=True` 模式；默认模式下，字段类型变化时还需同步修改辅助类型或 `typedef`。

## 1. 目的与原则

用户可能在紧急调试时直接修改生成的 SV/C++，来不及修改 Python 模型、重新生成并重新集成。生成结果应是可阅读、可编译、可直接修改的普通代码；使用者不必维护指纹、schema 摘要、产物哈希或另行运行校验信息生成器。

以“修改一个字段需要找到并修改多少处”为主要衡量标准：

- 修改约束、方法、默认值时，直接修改相应声明或方法。
- 修改受支持字段的位宽、固定数组长度时，编解码尽量从实际类型声明派生，不要求修改重复常量。
- 增删、改名或重排传输字段时，允许修改声明和同类型附近的一份字段编解码清单；不得再分别维护 pack、unpack、字段数量和摘要。
- 不要求用户学习一套替代 SV/C++ 声明的宏 DSL，也不以自动解析修改后的源码作为运行前置步骤。
- 生成代码正常编译、执行不依赖生成器清单或源 Python 包；既有运行时依赖仍可保留。

手工修改是正式支持的使用路径，不要求进入特殊的“紧急模式”。用户也不需要先设置一组关闭检查的选项。

这不使不同端自动获得相同的字段布局。若修改了传输布局，参与通信的实现仍需使用匹配的编解码；只运行修改后的原生模型而不传输时，不要求修改其他语言的模型。项目不承诺从任意手改代码自动恢复 Python 模型或覆盖率数据库映射。

## 2. 当前实现与需要解决的问题

当前代码入口包括：

| 位置 | 当前职责与问题 |
| --- | --- |
| `python/svtypes/object.py` | 同时输出声明、业务能力、对象注册、pack/unpack 与描述信息；对象头写入并验证 encoding fingerprint；pack/unpack 分别生成字段代码 |
| `python/svtypes/generator.py` | 输出代码及 schema/coverage/产物清单；生成检查与运行消费需要明确分离 |
| `python/svtypes/schema.py` | 提供声明与编码描述、显式 `checked_unpack()`；这些接口仍有独立用途 |
| `svtypes_runtime/sv/svtypes_pkg.sv`、`svtypes_runtime/cpp/svtypes.hpp` | 协议解析与预期类型、字段数量、指纹比较目前关联在一起 |

仅把指纹比较关掉，不能解决声明与 packer 中重复位宽、分别维护两个字段遍历的问题。仅把辅助代码移到别的文件，也不能解决修改牵连。因此需要同时调整产物组织、类型派生、字段编解码和诊断策略。

## 3. 目标架构

```text
Python 声明 / 冻结的公开设计信息
                 |
        生成内部表示（按职责拆分）
                 |
     +-----------+--------------+----------------+
     |                          |                |
设计代码                   编解码适配         诊断元数据
类型/字段/方法              字段访问与顺序      来源/摘要/预期布局
约束/covergroup             通用运行时调用      显式校验入口
     |                          |                |
     +--------- 正常运行 -------+      用户主动请求时使用
```

内部表示至少区分设计声明、字段编解码计划、运行时适配和诊断数据。它是生成器内部组织方式，不新建一套语义 IR，不要求第三方后端依赖私有实现。

同一实现供 `generate()`、`to_sv_obj()`、`to_cpp_obj()` 使用，避免只有某个输出路径变得可维护。后端 SDK 仍消费公开 Design Manifest，不反向依赖核心渲染器；可采用同样的产物职责划分。

## 4. 生成产物组织

### 4.1 主体代码优先

主体依次展示类型、字段及默认值、构造与用户方法、约束、covergroup 和可见随机化能力。用户期望修改的功能必须能在这里直接定位。

编解码、对象注册、格式化、生成器诊断放在明确命名的辅助部分。长摘要、来源表和验证表不插入字段之间，也不混入约束和方法主体。

多文件输出的建议结构如下；文件名属于生成布局，实施时保持现有入口文件可引用：

```text
design.sv / design.hpp          主体与稳定编译入口
support/                       编解码和必要运行时适配
metadata/                      schema、来源、产物摘要等静态输出
diagnostics/                   可选的严格校验代码
```

不要拆成每个小函数一个文件。编解码清单按类型集中，主体中给出一处清楚的定位说明。SV 中必须处于类作用域的部分使用短声明、适当的 include 或类外定义；不得为了分文件破坏访问权限、继承、virtual 或参数作用域。具体拆分先做编译原型验证。

返回单段文本的旧接口保留可独立使用的结果，采用相同顺序和明确辅助区段，不返回隐式缺少 include 文件的代码。

### 4.2 静态清单不是执行许可

manifest 的摘要表示生成时快照。手工修改代码后，普通编译和运行不比较 artifact hash，不读取清单来确认“是否允许执行”。显式调用生成检查或诊断工具仍可报告差异。

默认运行不要求同步 schema 文件。需要消费 schema 的导出工具或覆盖率映射工具仍按各自契约使用它；不得把旧快照当成手改后的最新语义，也不得为了方便手改而取消数据库合并的语义判断。

重新生成是另一项显式操作，不自动把手改内容回写模型。生成器不得悄悄覆盖已修改的受管文件：提供差异/独立输出或显式覆盖选择；这项生成时保护不成为应用启动检查。

## 5. 减少字段修改的牵连

### 5.1 从实际声明派生

编解码适配层优先引用字段实际类型或公开命名类型；宽度、维度、元素类型和长度尽量由编译器或实际容器获得。SV 的 `$bits`、维度查询与类型引用，C++ 的类型推导与容器 traits，是待验证的实现手段，不用它们改变现有字节协议。

必须区分“类型总位宽”和“传输编码”：

- unpacked struct 继续按字段编码，不使用内存布局或填充字节；
- packed struct 仍遵守现有字段 codec 契约，不能因为得到总位宽就改为整体紧凑打包；
- 2-state、4-state、符号、枚举底层类型、字节序与字段策略不由位宽单独决定；
- 动态容器使用运行时长度，固定容器使用实际声明维度；handle 继续保持对象身份和共享/循环图语义。

无法可靠自动派生的编码类别使用一处显式适配，不散布到业务声明和两个方向的函数中。字段换成不同编码类别时，允许同步调整这一处适配。

### 5.2 一份字段编解码清单

每个类型只维护一份有序的传输字段访问清单，pack/unpack 复用同一遍历。下面是结构示意，不是已经存在的 API 或可直接编译的 SV：

```text
Packet 的字段编解码过程(operation):
    operation.field(this.opcode)
    operation.field(this.payload)
```

operation 表达读、写及必要的计数行为；共享适配负责具体编码。字段访问使用明确的 owner 限定，避免字段名与 `offset`、`bytes` 等局部变量冲突。继承只遍历一次父类字段，保持现有线序；不序列化的字段不进入清单。

SV/C++ 不必采用相同的实现语法。SV 需要先验证 ref 实参、参数化类型、4-state 和动态容器的适配可行性；不能以运行时逐字段字符串查找或反射表解释器换取单清单，也不能遍历两次整个对象图来取得字段数量。

字段数量由清单结构或编译期结构派生。若目标语言需要计算过程，它只能做轻量的直接字段计数，不读字段值、不递归遍历容器或句柄、不构建诊断描述；性能验收不通过则重新选择清单的实现形式。

SV 没有供本方案任意枚举已编译类/struct 成员的通用反射机制，因此不承诺“新增声明后编解码自动发现新成员”。需要维护声明和一份清单，但不能要求用户额外计算字段数或任何校验摘要。

## 6. 运行检查的边界

将附加诊断与完成操作所必需的处理分开，不能用一个 `disable_checks` 关闭所有错误处理。

| 行为 | 默认正常运行 | 显式严格诊断 |
| --- | --- | --- |
| 产物哈希、源模型与生成文件一致性 | 不执行，不读取相关文件 | 可检查并报告手改差异 |
| schema / encoding fingerprint 的一致性比较 | 不执行，不主动构建描述或计算摘要 | 执行，缺少可信描述时明确无法验证 |
| 预期字段数与对象头字段数的附加一致性比较 | 不作为手改门禁 | 比较并报告 |
| 格式解析、实际读取所需的长度与边界处理 | 保留 | 保留 |
| 不支持的 wire 格式版本、非法记录种类、无法解析的对象引用 | 明确报错，不能猜测布局继续 | 同左 |
| 对象身份注册与引用解析、事务与必要资源管理 | 保留；它们属于操作语义 | 同左 |
| 类型身份用于选择正确解码器 | 保留必要的分派；不能以关闭诊断把未知类型当成另一个类型 | 可增加预期身份比较 |
| 随机失败、illegal bin、无效 DSL 等功能语义 | 保持既有语义 | 不受本选项影响 |
| 覆盖率数据库定义身份与合并规则 | 保持既有契约 | 不受本选项影响 |

不因默认关闭诊断而输出每次调用警告、记录差异或计算隐藏摘要。正常调用路径只承担实际功能和必要解码工作。

目标 API 使用统一的操作/上下文诊断策略，概念值为 `off` 与 `strict`，默认 `off`；正式参数命名随接口审查确定。策略由顶层操作确定并传递，嵌套操作继承，不逐字段读取环境变量或可变进程全局开关。独立并发上下文可以采用不同策略。

已有 `checked_unpack()` 名称明确表示校验，因此它本身就是用户主动选择严格校验的入口；不能改成不检查的同名方法。普通 `unpack()` 的目标默认策略与此分开。schema 查询、显式生成检查和测试工具也不因本方案失去功能。

严格诊断与“证明手改后的代码和模型一致”不同。保留的旧指纹只能描述生成时快照；相同旧指纹不能证明手改后的实际布局相同。需要这种证明时，用户主动重新生成/审查实际布局并提供新描述；普通运行不得要求这一流程。

## 7. 协议兼容与元数据处理

先保持现有对象头字段、字节位置及字段编码。默认关闭指纹比较不等于从包里删除 32 字节指纹，也不把裸 struct 改成带对象头编码。

过渡实现可继续写入生成时的静态指纹并读取其占位字节，但默认不据此判定手改布局是否有效；此时它只代表原生成快照。运行时不重新计算 SHA，也不要求用户更新常量。若诊断元数据被省略，如何表示不可用必须有明确定义，不自行把全零值解释为旧格式中的通配符。

旧接收端可能仍强制检查指纹，不能承诺新发送端单方面控制旧接收端策略。先完成 Python/SV/C++ 同版本运行时的策略对齐与测试，并明确记录新行为；已有 capability 不重新解释成“支持可选诊断”。若需要新的能力标识，由本项独立引入。

任何实际 wire 格式变化另行版本化，不以“辅助信息”名义破坏既有解析。当前 struct 数据契约和二进制格式文档在对应实现阶段同步更新；在此之前它们仍描述当前行为。

## 8. 与其他架构的关系

- 这是核心生成器及运行时的可维护性改进，不要求用户采用后端 SDK、GUI 或新语言后端。
- 后端 SDK 的路径校验、未知构造拒绝、确定性输出和原子写入仍适用于生成阶段；不转换成生成应用的启动校验。
- Design Manifest 继续表示生成输入快照。手改后不强求它变为运行状态的真相，也不允许扩展据此宣称手改代码已通过语义验证。
- `encoding_fingerprint`、`schema_fingerprint` 和 coverage semantic digest 保留各自含义，不合并成一个可以全部关闭的“校验信息”。
- 调试打印、来源跟踪等可选能力使用公共辅助代码或延迟构建的数据，避免复制大段诊断逻辑到每个生成类。必需的随机和覆盖率逻辑不因体积较大就被误当成可删检查。

## 9. 分阶段实施与准入

| 阶段 | 内容 | 完成标准 |
| --- | --- | --- |
| M0 基线与小型原型 | 盘点三侧检查调用；为 scalar、packed/unpacked struct、容器、继承和 handle 建立修改牵连表；验证单清单与类型派生 | 对比手改前后所需修改位置；原型在 C++ 与配置的远程 SV 目标编译运行；公开记录采用中性术语 |
| M1 产物分层 | 统一生成内部职责和主体/辅助布局，保持旧文本入口可用 | 未手改时字节契约、随机与覆盖率行为不变；可独立编译产物，无新增插件依赖 |
| M2 编解码去重 | 单字段清单、声明派生、统一 owner 限定；派生字段数 | 位宽/固定长度修改不维护重复常量；增删字段只改声明及一份清单；所有方向字节对齐 |
| M3 诊断分离 | 普通路径默认 off，显式 strict 与 checked API 保留；三侧上下文一致 | 默认路径无附加摘要构建/比较/文件检查；格式解析仍正确；新旧运行时行为与能力说明完整 |
| M4 手改场景验收 | 不重跑生成器的实际修改、编译、运行；文档及性能对比 | 下述场景通过，证据区分当前实现与目标；再宣布完整支持 |

M0 先解决实现语言约束，不能将未经编译验证的单清单设计作为已交付能力。阶段可以独立提交，但 M1 仅使输出清楚，不足以宣称紧急手改目标已完成。运行默认值变化在 M3 明确发布，不提前改写当前契约。

## 10. 验收场景

所有手改测试都从真实生成结果出发，随后直接修改目标源文件并编译执行；禁止通过重新生成、更新摘要或绕过实际传输来替代验证。

| 修改/操作 | 允许的手工修改范围 | 必须观察的结果 |
| --- | --- | --- |
| 约束、方法体、默认值 | 对应主体位置 | 新行为生效，无生成文件一致性门禁 |
| scalar 位宽、固定数组长度 | 实际声明；必要时调整本身依赖旧范围的业务语句 | 适配器跟随声明；不手改 pack/unpack 常量或摘要 |
| 增删、重排传输字段 | 声明与一份字段清单 | pack/unpack 顺序一致，字段数无需维护 |
| packed/unpacked、4-state、嵌套容器 | 类型声明及必要的单处编码类别适配 | 保持既有字段编码规则，不意外改成内存拷贝或整块位编码 |
| 字段名与适配器局部变量重名 | 只改字段及清单 | 明确 owner 访问，无遮蔽导致的误读写 |
| 共享句柄、null、循环图 | 同上 | 引用身份不因诊断 off 而失真 |
| 删除诊断 sidecar 后普通编译运行 | 无补充元数据 | 正常运行不读取 sidecar；显式 strict 缺失描述则清楚报错 |
| 仅业务修改后运行覆盖率 | 业务代码 | 实际采样符合修改；不把旧 coverage 映射伪装成重新验证结果 |
| 默认与 strict 分别运行 | 顶层显式策略 | 默认无摘要工作；strict 能发现已提供描述的真实不匹配；checked API 仍检查 |
| 截断数据、非法引用或不支持格式 | 不修改代码 | off 也不能越界、伪造对象或把损坏数据当作成功 |
| Python/SV/C++ 对应端更新 | 实际匹配声明/字段顺序 | 三侧往返值和字节一致，无手算校验信息 |

性能基线覆盖小对象批量编解码、大容器、共享图和无编解码的随机/采样工作。记录耗时、分配、产物尺寸与辅助代码占比；重点检查操作适配是否引入逐字段动态分派、大对象复制或二次图遍历。默认模式零诊断摘要计算/比较是硬要求；正常编解码相对基线的回退必须在发布前解释并解决，不能以可维护性为由默认接受。

## 11. 明确不承诺的行为

本方案不自动传播一端的结构修改到另一端，不在运行时反射恢复所有成员，不自动重写 Python 模型，不保证重新生成无损保留任意手改内容，也不取消功能语义与协议解析错误。它承诺的是：改实际功能所必需的代码，能就近改、少处改；无需另外维护校验材料才能运行。
